# Переезд на сервер: картинки, дубли слов, VPS

План на момент, когда бот перестаёт жить на Mac и уезжает на VPS к реальным людям.
Все цифры — замеры (живой API, живая база), а не оценки. Где оценка — помечено.

**Статус: часть сделана.** Картинки через API уже написаны и включены (см. ниже). Остальное — план.
Что уже сделано — провайдеры LLM, см. `docs/llm-models.md`.

Связанные документы: `docs/llm-models.md` (модели и их цена), `docs/architecture.md` (карта системы),
`docs/image-samples/` (образцы картинок пяти моделей).

---

## Решения, которые уже приняты

Коротко, чтобы не перечитывать всё:

1. **Картинки — через Gemini 3.1 Flash Lite Image ($0.034), не через FLUX.** FLUX в 67 раз дешевле,
   но качество заметно хуже — смотрели глазами, образцы в `docs/image-samples/`.
2. **Стиль по умолчанию — акварель, а не комикс.** Акварель читается лучше на 512 px.
3. **Лимиты на картинки нужны**, но по типу слова: трудным (3+ провала) — бесплатно и заранее,
   остальным — по кнопке.
4. **Кэш обогащения по языку** — главный рычаг экономии на тексте (~50% токенов).
5. **VPS — Hetzner CX32 (8 ГБ),** не CX22: Kokoro с torch держит 1.6 ГБ.

## 1. Картинки через API

### Почему это обязательно

Сейчас картинки рисует `FluxSynth` (`src/images/images.ts`) — локальный FLUX.1-schnell 4-bit через
`mflux`, модель ~10 ГБ, пик памяти ~12 ГБ, ~20 с на картинку. **Это Apple Silicon: `mflux` требует
Metal.** На Linux-VPS не заработает вообще. Значит, при переезде выбор один — внешний API.

### Куда встраивается

**Сделано.** `ApiSynth implements ImageSynth` живёт в `src/images/images.ts` рядом с `FluxSynth`,
`ImageSynth` (`draw(prompt): Promise<Buffer>`) не менялся, `ImageService` — тоже. Выбор в `src/index.ts`:

```ts
const imageSynth = config.imageApiKey && config.imageModel
  ? new ApiSynth({ apiKey, model, title: "WordBoss" })   // API — нужен на Linux
  : config.mfluxBin
    ? new FluxSynth(config.mfluxBin)                     // локальный FLUX — Apple Silicon
    : undefined;
```

Включение — `.env`: `IMAGES_ENABLED=1` + `IMAGE_API_KEY` + `IMAGE_MODEL`. Ключ важнее `MFLUX_BIN`:
если заданы оба, рисует API (и в лог уходит предупреждение). При старте видно, кто рисует:
`Картинки: API google/gemini-3.1-flash-lite-image`.

**Что выяснилось на живом API (не было видно из замеров):**

- Нужен `modalities: ["image", "text"]` — без него модель отвечает **описанием** вместо картинки.
- Картинка приходит не отдельным полем, а `choices[0].message.images[0].image_url.url` как data-URL.
- **Модель возвращает 1408×768, а не квадрат** (проверено 4 раза). Локальный FLUX отдавал 512×512.
  `compressPicture` жмёт по `fit: "inside"`, поэтому карточка становится широкой (512×279).
  Для Telegram это нормально, но вид карточки меняется — если захочется квадрат, резать надо здесь.
- Ответ 0.5–2 МБ, после сжатия 25–48 КБ. Время 5–8 с.
- **Ловушка:** если в промпт положить инструкцию («придумай картинку…»), а не готовую сцену, модель
  отвечает текстом без картинки. Боевой путь (`buildImagePromptPrompt` → готовая английская сцена)
  работает, но ошибку теперь видно в логе: `no picture, it answered with text: …`.

`ImageService` при этом не меняется: дедуп по `word.id`, `inFlight`, запись `imageFileId` — всё
остаётся. Последовательная очередь (`enqueue`) сейчас нужна из-за памяти FLUX; у API это ограничение
не нужно, но очередь полезна как тормоз расходов, поэтому оставляем.

### Замеры: модели

Реальные вызовы через OpenRouter, промпт — настоящий (`buildImagePromptPrompt` → `imagePrompt`),
сжатие как в бою (`sharp`, 512 px, JPEG q82):

| модель | за картинку | время | JPEG после сжатия |
|---|---|---|---|
| **`google/gemini-3.1-flash-lite-image`** | **$0.0336** | 5–8 с | 25–48 KB |
| `google/gemini-2.5-flash-image` (Nano Banana) | $0.0387 | 6–7 с | 44–89 KB |
| `google/gemini-3.1-flash-image` (Nano Banana 2) | $0.0672 | 10 с | 39–45 KB |

**Вывод: переплата в 2 раза не покупает ничего.** Дешёвая 3.1-flash-lite даёт композицию чище и
меньше лишних деталей, чем дорогая. Это закреплено образцами.

### Замеры: качество (смотрели глазами)

Слова с переносными смыслами: `set off` (отправиться в путь), `gauge` (оценивать), `bank` (берег).
Образцы — `docs/image-samples/`.

| модель | что получилось |
|---|---|
| FLUX.1-schnell (локально, как сейчас) | **заметно слабее.** На `gauge` не понял задачу: мимика читается как недовольство, поза неестественная. На `set off` человек вылезает из каменного портала вместо двери коттеджа. Рисует «по словам», не понимая сцены. |
| Gemini 3.1 Flash Lite | понимает смысл: рюкзак, карта, рассвет, дверь; изучающий взгляд; граница воды и берега. |
| Gemini 2.5 Flash Image | сравнимо с lite, но дороже. |
| Gemini 3.1 Flash Image | больше «глянца», для карточки не преимущество. |

**Это развернуло первоначальное решение.** Сначала план был «FLUX за $0.0005 как основной» — по цене
он в 67 раз дешевле. Но качество видно глазом, и на 10% слов разница $20/мес против $0.30 не стоит
того, чтобы портить продукт. **Берём Gemini.**

### Стиль: перейти на акварель

Сейчас `DEFAULT_IMAGE_STYLE = STYLE_PRESETS[0].style` — комикс (`src/images/images.ts:62`).

**Акварель читается лучше.** Halftone-точки комикса на 512 px дают грязь в тенях; акварель мягче и
понятнее для запоминания. Образцы `*_lite-watercolor.jpg`.

**Осторожно: просто переставить `STYLE_PRESETS` нельзя.** Индекс стиля уходит в callback data кнопки
«Перерисовать» (`mnemonic.ts:143`: `STYLE_PRESETS[cb.how]?.style`), а `tests/redraw.test.ts:63` жмёт
`STYLE_PRESETS[1]`. Перестановка массива сломает и старые кнопки в уже отправленных сообщениях, и тест.

Правильный путь — **не трогать порядок, а сменить умолчание**:

```ts
// Порядок STYLE_PRESETS — это ещё и нумерация кнопок в старых сообщениях, менять нельзя.
export const DEFAULT_IMAGE_STYLE: string = STYLE_PRESETS[1].style; // акварель
```

Плюс проверить `IMAGE_STYLE` в `.env` — он перебивает умолчание. И убедиться, что `redraw.test.ts`
не ждёт стиль по умолчанию равным комиксу.

### Что брать вместо/кроме Gemini (справочно)

FLUX живёт не на OpenRouter (проверил каталог — image-output моделей там 12, FLUX среди них нет),
а на DeepInfra:

| модель | за картинку |
|---|---|
| `stabilityai/sdxl-turbo` | $0.0002 |
| `black-forest-labs/FLUX-1-schnell` | $0.0005 |
| `PrunaAI/p-image` | $0.005 |
| `black-forest-labs/FLUX-1-dev` | $0.009 |

Годится как «экономный режим», если картинки вдруг станут массовыми. Требует отдельного ключа
DeepInfra (анонимного доступа нет — проверено, 401).

«нажимать будут редко»):

|---|---|---|---|
| **Gemini 3.1 Flash Lite** | 7 300 | **$245** | **$20.44** |
| Gemini 2.5 Flash Image | 7 300 | $283 | $23.54 |

### Лимиты на картинки

Пользователь хочет заложить лимиты. **Лимит «N картинок в месяц на человека» — плохой:** человек
нажал, ему отказали, он не понимает почему.

Лучше — **лимит по типу слова**, он же экономически осмысленный:

- **Трудные слова (3+ провала, `HARD_AFTER_LAPSES`)** — картинка бесплатна и генерируется заранее.
  Таких слов мало, а польза от картинки там максимальная.
- **Остальные** — по кнопке, одна на слово. Повторное нажатие денег не тратит: `PictureStore`
  ключует файл по `id-term-translation`, а `ImageService.inFlight` не даёт нажать дважды.
- **«Перерисовать»** — с лимитом (например, 3 в день на человека). Это единственное место, где
  человек может жечь бюджет бесконечно.

**Почему это важно:** сейчас `BackgroundPainter` (`src/images/painter.ts`) рисует заранее **все** слова
без картинки, никого не спрашивая. Замер на живой базе: **249 слов, нарисовано 247 картинок, а кнопку
нажали только для 90.** То есть фон даёт 2.7-кратную переплату — на Gemini это $2 453 вместо $883
в год. **На платном API фоновый художник надо выключать или ограничивать только трудными словами.**

### Что ещё надо сделать для картинок

- [x] `ApiSynth implements ImageSynth` — POST в OpenRouter, разбор data-URL в буфер.
- [x] `AbortController` на таймаут (60 с; норма 5–8 с, но хвосты бывают) — как в `src/llm/openrouter.ts`.
- [x] Декодировать base64 сразу в буфер, не хранить data-URL (ответы 0.5–2 МБ).
- [x] Конфиг: `IMAGE_API_KEY`, `IMAGE_MODEL` в `src/config.ts` + `.env.example`.
- [x] `redactLogs` для `IMAGE_API_KEY` (инвариант 7 — «завели третий секрет, вырежьте и его»).
- [x] Тесты `ApiSynth` — подменой `fetch`, без сети (`tests/api-synth.test.ts`, 7 тестов).
- [x] **Фоновый художник выключен** (`IMAGES_BACKGROUND=0`). Это остановило переплату сразу:
      на момент выключения в базе было **159 слов без картинки** — фон принялся бы рисовать их все
      (примерно $5.34, если бы дошёл до конца). Состояние видно в логе:
      `Картинки: API <модель>, фон выключен (только по кнопке)`.
- [ ] **Вернуть фон, но только для трудных слов** (3+ провала, `HARD_AFTER_LAPSES`). Сейчас фон
      выключен целиком, поэтому трудные слова тоже рисуются только по кнопке. Это осознанный
      компромисс: так безопаснее по деньгам, но польза картинки для трудного слова теряется.
      `BackgroundPainter` уже умеет сортировать трудные слова первыми — надо сузить выборку,
      а не переписывать цикл.
- [ ] Счётчик расхода: таблица `image_spend(user_id, day, count, cost)`. Без неё лимит — вслепую,
      и не видно, кто жжёт бюджет.

## 2. Защита от дублей слов

### Что уже есть (и это больше, чем кажется)

| механизм | где | что ловит |
|---|---|---|
| `normalizeTerm` — `trim().toLowerCase().replace(/\s+/g, " ")` | `src/services/words.ts:42` | регистр, лишние пробелы |
| `uniqueIndex("words_room_term_idx")` на `(room_id, term_normalized)` | `src/db/schema.ts:114` | последний рубеж на уровне БД |
| `findWord` перед вставкой + `onConflictDoNothing` | `words.ts:80,100` | обычный путь и двойной клик |
| `filterNewItems` — чистит пачку до показа | `words.ts:109`, `batch.ts:78` | дубли **внутри** пачки и против комнаты |
| `word-sets` — свой `seen` при импорте набора | `word-sets.ts:113` | дубли внутри набора |
| `edit.ts` — `clash` при смене термина | `edit.ts:35` | переименование в существующее слово |

Живая база это подтверждает: **249 слов, 247 уникальных** — и оба «дубля» не ошибка, а разные комнаты
(`work` в комнатах 2 и 6, `beset by` в 2 и 4). Внутри одной комнаты дублей нет.

### Где дырки

1. **Дедуп только внутри комнаты.** Это сознательно (у каждого свой словарь), но при росте это значит:
   одно и то же слово десять человек готовят десять раз — **десять вызовов LLM, десять картинок,
   десять озвучек**. Слова общие для языка, а не для комнаты.
2. **Морфология не учитывается.** `set off` и `set-off`, `bank` и `banks`, `work` и `to work` — для
   `normalizeTerm` разные слова. На живых людях это будет частой жалобой.
3. **Нет канонизации.** «то же слово, но с артиклем» (`the bank`), с пометкой части речи
   (`bank (n)`) — снова новое слово.
4. **Дедуп не переживает гонку между процессами.** `findWord` + `onConflictDoNothing` спасают внутри
   одного процесса; уникальный индекс — единственное, что держит при нескольких воркерах. Индекс есть,
   этого достаточно, но полагаться на `findWord` как на защиту нельзя.

### Что делать

**Шаг 1 — кэш обогащения по языку (даёт больше всего).** Дубли внутри комнаты уже невозможны; потери
идут от того, что одно слово в разных комнатах считается заново. Ввести таблицу
`word_enrichment(language, term_normalized, translation, explanation, example, transcription_uk,
transcription_us, mnemonic, usefulness, usefulness_note, created_at)` с уникальным индексом
`(language, term_normalized)`. `prepare-word` сначала смотрит туда:
- **попадание** — enrichment не зовём вообще: 0 токенов, 0 секунд вместо 5 вызовов. Слово в комнату
  всё равно вставляется своё (свой `id`, свой `context`, свои карточки) — меняется только источник
  полей.
- **промах** — считаем как сейчас и пишем в кэш.

Схема портируемая (инвариант 3 соблюдён), таблица пополняется по ходу, вручную наполнять не надо.
Эффект на 200 человек при 1 слове в день: если половина слов повторяется между комнатами, экономия
**~50% текстовых токенов** — то есть $13.60/мес превращаются в ~$7.

**Шаг 2 — мягкая нормализация для поиска дублей.** Не трогая то, что хранится и показывается:

```ts
/** Ключ поиска дублей: регистр, пробелы, дефисы, ведущий to/the, хвостовая пометка части речи. */
function dedupKey(term: string): string {
  return normalizeTerm(term)
    .replace(/[‐‑–—-]/g, "-")       // разные дефисы — один
    .replace(/^(?:to|the)\s+/, "")  // to work = work
    .replace(/\s*\((?:n|v|adj|adv|prep|phr)\)\s*$/, "");
}
```

Это **не** замена `normalizeTerm` в `termNormalized` (там индекс и поиск) — второй, более мягкий ключ
для проверки «такое уже есть?». Множественное число намеренно не трогаем: `bank` и `banks` — иногда
разные слова, ошибочно склеить хуже, чем оставить дубль.

**Шаг 3 — сказать человеку, что слово уже есть.** Сейчас `saveWord` возвращает `duplicate`, и это
где-то превращается в невнятный ответ. Надо показывать: в какой комнате, кто добавил, и предложить
«всё равно добавить» — потому что у человека может быть причина (свой контекст).

### Что не делать

- **Не переносить уникальность на уровень языка.** Люди правда учат разное; запрет «это слово уже
  есть у Васи» — сломанный продукт.
- **Не гоняться за стеммингом.** Полноценная лемматизация тянет словарь и морфологию, а ошибётся она
  незаметно. Мягкий ключ из шага 2 закрывает 90% случаев бесплатно.

## 3. VPS: сколько стоит

Цифры — из живых API провайдеров (`api.vultr.com/v2/plans`, `api.linode.com/v4/linode/types`).
Hetzner с этой сети недоступен (DNS), его цены — публичный прайс, помечены как справочные.

| тариф | vCPU | RAM | диск | $/мес | $/год |
|---|---|---|---|---|---|
| **Hetzner CX32** (справочно) | 4 | 8 ГБ | 80 ГБ | **7.59** | 91 |
| Hetzner CX22 (справочно) | 2 | 4 ГБ | 40 ГБ | 4.59 | 55 |
| Vultr `vc2-2c-4gb` | 2 | 4 ГБ | 80 ГБ | 20.00 | 240 |
| Vultr `vhf-2c-4gb` | 2 | 4 ГБ | 128 ГБ | 24.00 | 288 |
| Linode `g6-standard-2` | 2 | 4 ГБ | 80 ГБ | 24.00 | 288 |
| Vultr `vc2-4c-8gb` | 4 | 8 ГБ | 160 ГБ | 40.00 | 480 |
| Linode `g6-standard-4` | 4 | 8 ГБ | 160 ГБ | 48.00 | 576 |

### Что реально нужно

- **RAM: 4 ГБ минимум, 8 ГБ комфортно.** Замер `footprint` на живом Mac: **сам бот — 88 МБ**, но
  рядом `kokoro_server.py` (Python + torch) — **1573 МБ**. Kokoro ставится на Linux (`tools/tts`,
  python 3.12 + `kokoro==0.9.4`, модель ~330 МБ), то есть эти 1.6 ГБ переезжают на VPS вместе с ботом.
  Уходит только FLUX: 10–12 ГБ под MLX больше не нужны. Итого ~2 ГБ занято, плюс всплески `sharp`
  и WAL. Если озвучку отдать внешнему API — хватит и 2 ГБ.
- **Диск: 80 ГБ.** `node_modules` — 495 МБ. Данные: 6.4 ГБ в год на 200 человек (замер из
  `docs/llm-models.md`). Бэкапы (14 копий в `data/backups/`; сейчас 84 МБ на 113 МБ данных — то есть
  удваивают) → ~26 ГБ на два года. На 40 ГБ влезает, на 80 ГБ спокойно.
- **CPU: 2 vCPU достаточно.** Вся работа — ожидание сети. `sharp` и `better-sqlite3` — короткие вспышки.

### Рекомендация

**Hetzner CX32 (4 vCPU / 8 ГБ / 80 ГБ, ~$7.59/мес).** Не CX22: 4 ГБ формально хватит, но Kokoro
с torch любит всплески. Разница $3/мес — не та экономия, ради которой стоит рисковать OOM.
Против Vultr/Linode это в 3 раза дешевле за больше железа. Запасной вариант — Vultr `vhf-2c-4gb`.

а после кэша обогащения текст дешевеет вдвое. Дальше экономить надо там, и рычаг — кэш.

## 5. Что ещё сломается на Linux

Это не про деньги, но всплывёт в тот же день.

**Озвучка — второе место после картинок.** Нашёл при замере памяти: Kokoro на VPS поедет (python +
`kokoro==0.9.4`, ~330 МБ модель, 1.6 ГБ RAM), а запасной синтез нет — `MacSaySynth` вызывает `say` и
`ffmpeg`, и `say` есть только на macOS. При этом `LanguageAwareSynth` отправляет **корейский всегда
через `say`** (`src/speech/tts.ts:69` — у Kokoro корейского нет). То есть на Linux корейская озвучка
отвалится полностью, английская — только если Kokoro поднялся. Варианты: `espeak-ng`/Piper как
запасной, либо корейский голос у внешнего TTS-API. **Решать до переезда.**

**Масштабирование (из `docs/architecture.md`):**
1. **Long polling, а не webhook.** Один процесс на токен: второй экземпляр получит 409 (уже ловилось
   на живом боте). Для роста — webhook.
2. **12 хранилищ держат состояние в памяти процесса** (`drafts`, `pickers`, `edits`, `batches`,
   `room-names`, `talks`, `translations`, `duels`, `drills`, `pending-mistakes`, `practice`,
   `picture-wishes`) — при рестарте теряются. Персистится только `ExerciseStore`. Выносить в БД.
3. **SQLite в WAL** — для чтения хватает, на запись один файл на одной машине. Дальше Postgres
   (схема писалась переносимой, инвариант 3).
4. **`Limiter(3)`** — 3 одновременных запроса на процесс. Потолок ≈64 800 слов/день на flash-lite.
