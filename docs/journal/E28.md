# E28 — Один процесс: падение между двумя записями оставляет данные в промежуточном состоянии

## Спека

Три места писали двумя запросами без атомарности:

- ответ на карточку (`UPDATE cards` → `INSERT review_logs`): падение теряет урон, ленту боя, отмену и
  статистику, но сдвигает расписание;
- раздача слова участникам (`INSERT words` → `createCards`): часть участников не получает карточку,
  и слово для них невидимо навсегда;
- разбор пачки.

Приёмка: для каждого места идемпотентный порядок либо догоняющая функция; тест, который рвёт второй
запрос, показывает, что система остаётся согласованной.

Решение владельца: точечно разрешить `db.transaction` — ровно там, где без него теряются данные.

## Главное открытие: асинхронная транзакция НЕ откатывает

Инвариант 3 в `AGENTS.md` уже разрешал `db.transaction`, и первой мыслью было обернуть записи
привычным `await db.transaction(async (tx) => …)`. Проба показала, что **это не работает**:

```
await db.transaction(async (tx) => { update(…); insert(…); throw });
→ reps 0 → 5, логов 1   (ничего не откатилось)
```

Причина в драйвере: `better-sqlite3` синхронный, его `transaction()` вызывает колбэк и сразу
завершает транзакцию — `async`-колбэк возвращает Promise, который никто не ждёт, и всё, что успело
выполниться, коммитится. Синхронный вариант работает:

```
db.transaction((tx) => { tx.update(…).run(); tx.insert(…).run(); throw });
→ reps 0 → 0, логов 0   (откатилось)
```

Поэтому в коде **синхронные** транзакции с `.run()`/`.all()`, а всё, что требует `await` (чтение слова,
расчёт урона, список участников), считается до входа. Это записано в комментариях у обоих мест —
иначе следующий человек напишет `async` и решит, что защита есть.

## Что сделано

**`src/services/review.ts` — `saveAnswer`.** `UPDATE cards` и `INSERT review_logs` в одной
синхронной транзакции. Условное обновление «если `reps` прежний» сохранено: два почти одновременных
ответа по-прежнему не засчитываются дважды. Результат (`ok`/`stale`) возвращается из транзакции
как значение.

**`src/services/words.ts` — `saveWord`.** Вставка слова **перенесена внутрь** транзакции: в первой
версии слово вставлялось до неё, и тест это поймал — падение на карточках оставляло слово без
карточек (`expected 1 to be 0`). Карточки вставляются синхронно в той же транзакции, а не через
асинхронную `createCards`.

**`src/bot/handlers/batch.ts` — `saveItems` не менялся.** Осознанно: каждое `saveWord` теперь
атомарно, а частичное сохранение пачки — не потеря данных, а честный частичный результат, о котором
человек видит число сохранённых слов.

**`tests/batch-atomic.test.ts`** — новый файл: слово и карточки появляются вместе; падение между ними
не оставляет слова; ответ засчитывается вместе с логом.

## Решения и причины

- **Синхронные транзакции, вопреки привычному `async`.** Выбор продиктован драйвером, а не стилем.
  Асинхронная версия выглядит правильной и молча не работает — это худший вид защиты, поэтому проба
  и объяснение оставлены рядом с кодом.
- **`createCards` не стала синхронной.** Её зовут ещё в `restoreCard` и `rooms`, и менять её сигнатуру
  ради одного места значило бы тронуть больше, чем нужно. В `saveWord` вставка раскрыта.
- **Раскрытая вставка дублирует `newCard`-логику.** Чанк в 200 строк скопирован из `createCards`.
  Дублирование здесь оправдано: альтернатива — сделать `createCards` синхронной, то есть прокинуть
  синхронность через несколько сервисов.
- **`saveItems` оставлен асинхронным.** Пачка сохраняет слова по одному, и обернуть весь цикл нельзя:
  внутри `checkAndCountWord` (нужен `await`) и `saveWord`. Атомарность на уровне слова достаточна —
  терять всю пачку из-за падения на пятом слове было бы хуже, чем сохранить четыре.

## Известные ограничения

- **`db.transaction` в сервисах теперь есть, и это отступление от прежнего инварианта.** Он записан
  в `AGENTS.md` как разрешённый точечно, но проверить «точечность» автоматически нечем: теста,
  который запрещал бы транзакции вне двух мест, нет.
- **Транзакция держит блокировку записи.** В SQLite она блокирует других писателей до конца
  — поэтому внутрь не кладётся ничего, что ждёт: ни модели, ни сети. Это соблюдено, но проверяется
  чтением, а не тестом.
- **`saveAnswer` считает урон до транзакции.** Между расчётом и записью состояние комнаты может
  измениться (например, бонус Дракона). Это не потеря данных, но урон остаётся тем, что был посчитан
  на момент ответа — что, в общем, правильно: ответ был тогда.
- **Падение процесса посреди транзакции** проверено только исключением внутри колбэка. Настоящий
  `kill -9` посреди записи не воспроизводился: SQLite гарантирует откат через WAL, но это гарантия
  драйвера, а не теста.
- **`restoreCard` и `rooms` не тронуты.** Там `createCards` вызывается вне транзакции; потери в этих
  путях меньше (восстановление карточки идемпотентно, раздача при создании комнаты повторяется), и
  в приёмку они не входили.
