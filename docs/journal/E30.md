# E30 — Новые слова падают всей кучей: дневной порции нет

## Спека

Слова добавляются пачками, и научиться им не поспеваешь: очередь отдаёт всё, что просрочено, а новых
слов может прийти десятки за раз одним нажатием. Нужна порция новых слов в день, настраиваемая лично.

Приёмка (из `docs/PLAN.md`):

- при порции 3 из 10 новых карточек за сутки выдаются ровно 3, остальные ждут следующего дня;
- ответ «✅ Знаю» и ответ по уже знакомой карточке порцию не тратят;
- при `0` выдаются все новые;
- повторения выдаются всегда, даже когда порция выбрана;
- смена настройки в `/settings` и в Mini App сохраняется и сразу меняет очередь;
- `npm test`, `npm run typecheck`, `cd app && npm run build` зелёные.

## Как было и почему это не работало

- `createCards` создаёт карточку через `createEmptyCard(now)` — слово доступно в ту же секунду.
- `dueItems`/`compareQueue` отдают всё просроченное: сначала повторения по `due`, потом новые по
  полезности. Потолка у новых нет ни в боте (карточки идут, пока есть), ни в Mini App
  (`QUEUE_SIZE = 20` — размер страницы: ответил 20 — придёт следующая пачка).
- Одно новое слово по шагам FSRS (`1m`, `10m`, затем дни) — это 2–3 ответа в первый день, поэтому
  пачка в 40 слов от друга превращается в долг, который не закрывается.

Замер на копии прод-базы (`data/eng-bot.sqlite`, бэкап 15 ноября, 11 человек, 929 карточек):

```
карточек State.New: 298
долг на человека:   user 2 — 120 новых + 162 просроченных повтора
                    user 1 — 101 новых + 147 повторов
                    user 3 —  55 новых + 220 повторов
```

То есть при таком долге новые либо не доходят никогда (повторения впереди), либо падают все разом.

## Что сделано

- `src/db/schema.ts` + `drizzle/0062_numerous_drax.sql` — колонка `users.new_per_day` (целое,
  по умолчанию 15, `0` — без ограничения). Миграция — один `ALTER TABLE`, данные не трогает.
- `src/services/review.ts`:
  - `newPortion()` — остаток порции: `{ limit, introduced, left }`, где `left = null` при `0`;
  - `introducedToday()` — сколько новых введено за локальные сутки человека (один запрос, см. ниже);
  - `withinPortion()` — фильтр очереди: новые сверх остатка отбрасываются, повторения проходят все;
  - `nextDue` и `dueQueue` (единственные точки выдачи для бота и Mini App) применяют порцию;
  - `countDueSplit` теперь отдаёт три числа: `fresh` (сколько можно показать сегодня) и `waiting`
    (сколько ждёт сверх порции).
- `src/bot/texts.ts` — `reminderText` печатает ожидающих отдельной спокойной строкой
  «📚 Ещё 105 новых слов ждут своей очереди — придут в следующие дни», а не пугающим «120 ждут знакомства».
- `src/services/reminders.ts` — тип `Reminder.due` получил `waiting`.
- Настройка в боте: `NEW_PER_DAY_CHOICES`, экран `new` в `settingsKeyboard`/`settingsText`,
  callback `np:<value>`, обработчик в `src/bot/handlers/stats.ts`.
- Настройка в Mini App: `appSettings` отдаёт `newPerDay` и `newPerDayChoices`, `appChangeSetting`
  принимает `{ newPerDay }`, `app/src/Settings.tsx` рисует раздел «🆕 Новые слова в день».

## Решения и причины

- **Порция — личная настройка, а не константа и не адаптивная формула.** Кто-то тянет 30 слов в день,
  кого-то выматывают 10; адаптивное правило («порция падает при росте просрочки») умнее, но его трудно
  объяснить человеку и трудно проверить тестом. Настройка объясняется одной строкой текста. Выбор
  вариантов (5/10/15/25/30/без ограничения) лежит в `NEW_PER_DAY_CHOICES` и отдаётся приложению
  с сервера, чтобы бот и Mini App не разошлись.
- **Счёт — по факту знакомства, а не по факту добавления.** Порция тратится на первый ответ по карточке
  за сутки. Отдельного счётчика в `usage_counters` нет намеренно: он разъехался бы с реальностью
  (пропуск дня, отмена ответа через «↩️», удаление карточки), а правильный счёт — один `NOT EXISTS`.
- **«✅ Знаю» не тратит порцию.** Это отказ от учёбы, а не знакомство: иначе человек, отметивший десять
  слов известными, упирался бы в потолок, не выучив ни одного. Проверяется по `stage = 'know'`
  (`KNOW_STAGE` в `services/goals.ts`).
- **Повторения не ограничены никогда.** Просроченное — это то, что уже начало забываться; отложить его
  значит потерять. Потолок касается только первой встречи со словом.
- **Лишние новые не удаляются и не теряются**, а ждут в том же порядке «сначала полезные» (`compareQueue`
  не менялся) — долг рассасывается сам, начиная с самых ходовых слов.
- **Запас «на 20 минут вперёд» (`LEARN_AHEAD_MS`) остался, но тоже режется порцией.** Он нужен, чтобы
  вернуть забытую в этой же сессии карточку, а не чтобы обойти дневной потолок.
- **Значение из кнопки и из HTTP проверяется по списку вариантов.** И кнопка бота, и `appChangeSetting`
  принимают только числа из `NEW_PER_DAY_CHOICES`: по этой колонке считается очередь, и произвольное
  число с клиента в неё попадать не должно.

## Проверки

```
npx vitest run tests/new-portion.test.ts  → 11 tests passed
npx vitest run                            → 122 files, 862 tests passed
npx tsc --noEmit                          → чисто
cd app && npm run build                   → собралось (763 модуля)
npm run docs:index && npm run docs:check  → 30 задач, согласовано
```

Замер подсчёта (проба на копии прод-базы): запрос `introducedToday` с `NOT EXISTS` по индексу
`review_logs(card_id)`, 1000 вызовов — 1 мс. Поэтому счёт на каждую карточку допустим, кэш не нужен.

Модель эффекта на копии прод-базы при порции по умолчанию 15:

```
user 2 (Артём):     сегодня новых 15 из 120, ждут 105, повторов 162
user 1 (Александр): сегодня новых 15 из 101, ждут  86, повторов 147
user 3 (Николай):   сегодня новых 15 из  55, ждут  40, повторов 220
```

Тесты, которые пришлось обновить, — не регресс, а захардкоженный список кнопок `/settings`
(`tests/welcome.test.ts`, `tests/bug.test.ts`): в меню появился пункт «🆕 Новые слова в день».

## Известные ограничения

- **Экран Mini App глазами не смотрел.** `app/src` не покрыт тестами и не входит в `tsconfig` корня;
  раздел проверен сборкой и чтением кода. Та же граница, что в E1 и E9.
- **Порция считается в момент показа, а не резервируется.** Два параллельных запроса очереди (бот и
  приложение одновременно) могут увидеть один и тот же остаток и показать чуть больше порции. Для
  одного человека с одним устройством это не наблюдаемо; жёсткая блокировка здесь стоила бы транзакции
  на каждую карточку.
- **Волна личных сообщений «знаешь?» не тронута.** Каждое слово друга по-прежнему приходит отдельным
  сообщением; это отдельная задача, а не алгоритм показа карточек.
- **Очередь по-прежнему грузит все просроченные карточки в память и фильтрует в JS** (как и до правки:
  `dueItems` и `inCurrentLanguage` уже работали так). На нынешних объёмах это незаметно; при десятках
  тысяч карточек фильтр надо будет перенести в SQL.
- **Тесты `docs/PLAN.md` про число задач не ведутся** — в документах намеренно нет чисел, которые
  меняются с каждым коммитом.
