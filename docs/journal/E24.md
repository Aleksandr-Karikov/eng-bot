# E24 — Два счётчика слов пишутся раздельно, и на границе лимит обходится

## Спека

`checkAndCountWord` читает дневной и недельный счётчики, потом пишет оба через `Promise.all`. Порознь
это правильно (отказ по недельному не съедает дневной), но между чтением и записью остаётся `await`,
поэтому два параллельных добавления при остатке 1 могут оба пройти.

Приёмка: `checkAndCountWord` — одна инструкция с по-строчными условиями; при исчерпанном недельном
дневной не растёт (проверяется `returning`: вернулись либо обе строки, либо ни одной); тест
`Promise.all` на 3× лимит при остатке 1 утверждает, что прошло ровно 1; инварианты целы —
`db.transaction` не появился, sqlite-специфичных методов нет.

## Что проверено пробами — и что оказалось неверным в постановке

Задача предлагала решение: одна инструкция `INSERT … VALUES (две строки) ON CONFLICT … DO UPDATE …
WHERE (kind = 'add_word' AND count < 50) OR (kind = 'add_word_week' AND count < 200) RETURNING`. Проба
показала, что **это не даёт** обещанного «либо обе строки, либо ни одной»:

```
дневной на пределе (50), недельный 10  → прошла только недельная       (верно)
недельный на пределе (200), дневной 0   → прошёл дневной, стало 1      (НЕВЕРНО)
```

Причина: `ON CONFLICT … DO UPDATE … WHERE` не проверяет условие при **вставке**. Если строки ещё нет,
она вставляется с `count = 1`, не спрашивая гейт. Отсюда же второй дефект: отказ по недельному всё
равно увеличивал дневной — ровно то, чего этот код обязуется не делать.

Вторая проба: условие по обоим счётчикам, вписанное в `DO UPDATE … WHERE`. На границе (49/199) проходила
только одна строка из двух — SQLite пересчитывал подзапрос для каждой строки уже после первой записи,
и вторая видела изменённое значение.

Третья проба: `WITH gate AS MATERIALIZED (…) UPDATE … WHERE gate` — правильный результат во всех
комбинациях, но требует, чтобы обе строки уже существовали.

## Что сделано

`src/services/limits.ts`:

- `ensureWordCounters` — идемпотентно заводит обе строки со счётчиком 0 (`INSERT … SELECT … WHERE гейт`
  + `ON CONFLICT DO NOTHING`). Заводит **только если места хватает по обоим**: иначе отказ оставил бы в
  базе нулевую строку, то есть след отказа — а существующий тест требует, чтобы при отказе дневной
  строки не было вовсе.
- `checkAndCountWord` — один `UPDATE` обеих строк с материализованным гейтом
  `(SELECT g.ok FROM (WITH g AS MATERIALIZED (SELECT (<оба предела>) AS ok) SELECT ok FROM g) AS g)`.
  Либо обе строки получают +1, либо ни одна; `returning` показывает, какие изменились. Для отказа
  упёршийся счётчик читается отдельно — иначе человеку не объяснить, какой лимит его остановил.
- `tests/word-room-limits.test.ts` — два теста: «параллельные попытки не сжигают дневной счётчик на
  отказах» и «при исчерпанном недельном дневной не растёт».

## Решения и причины

- **Два шага вместо одной инструкции.** Одна инструкция невозможна: `ON CONFLICT … WHERE` не действует
  на вставку, а `INSERT … SELECT … ON CONFLICT` в drizzle не собирается (он подставляет параметр в
  список колонок — проверено по `toSQL()`: `insert into "usage_counters" (...) ? AS user_id, …`).
  Разделение на «завести строки» и «посчитать один раз» сохраняет главное: **считает ровно одна
  инструкция с общим гейтом**, поэтому промежуточного состояния не бывает.
- **`MATERIALIZED` обязателен.** Без него SQLite пересчитывает подзапрос после каждой записи — проверено,
  на границе 49/199 проходила одна строка. Это не украшение синтаксиса, а условие корректности.
- **Отказ не оставляет строк.** `ensureWordCounters` под гейтом — иначе тест «отказ не сжигает дневной»
  падал бы на нулевой строке, и это правильно: нулевая строка — тоже след отказа.
- **Переносимость проверена.** `WITH … MATERIALIZED`, `INSERT … SELECT`, `UPDATE … RETURNING` есть и в
  SQLite, и в Postgres. `db.transaction` не появился; sqlite-специфичных методов (`.get/.all/.run`) в
  сервисе нет.

## Проверки

```
npx vitest run tests/word-room-limits.test.ts  → 20 tests passed
npx vitest run                                 → 122 files, 864 tests passed
npx tsc --noEmit                               → чисто
```

Тест проверен на старом коде (`git stash push src/services/limits.ts`) и падает по существу:

```
× параллельные попытки не сжигают дневной счётчик на отказах
  → expected [ …(2) ] to have a length of 1 but got 2
```

До правки две параллельные попытки при остатке 1 проходили обе, и дневной счётчик доходил до 12 вместо 11.

**Важная честная поправка:** первый вариант теста («3 параллельные попытки при остатке 1 по дневному»)
**проходил и на старом коде**. Причина — `better-sqlite3` синхронный, и в одном процессе настоящей
гонки не возникает. Наблюдаемое различие нашлось в другом месте: старый код писал дневной счётчик **до**
того, как выяснялся отказ по недельному, и человек терял место за то, что упёрся в другой лимит. Тест
переписан на этот сценарий.

## Известные ограничения

- **Настоящую гонку между процессами проверить нечем.** Бот однопроцессный, `better-sqlite3` синхронный,
  поэтому «два параллельных добавления» в тесте — это два `await` в одном процессе, а не два потока.
  Что две инструкции из разных процессов не могут обе пройти, следует из свойств транзакции SQLite
  (`UPDATE` с гейтом целиком внутри одной инструкции), но тестом это не воспроизведено.
- **`ensureWordCounters` — отдельная инструкция.** Между ней и считающим `UPDATE` теоретически может
  вклиниться другой процесс и выбрать последнее место. Тогда `UPDATE` просто не пройдёт целиком (гейт
  общий), то есть лимит не будет превышен — но одна попытка может получить отказ при наличии места на
  другой счётчик. В однопроцессном боте это недостижимо.
- **Лимиты передаются в SQL числом** (`${day.limit}`), а не как константа запроса. Это параметр, а не
  подстановка строки — инъекции нет, но при изменении `QUOTAS` гейт меняется вместе с ним автоматически.
- **`quotaUsed` для отказа читается двумя запросами.** Небольшая цена за точный текст отказа; на отказе
  бывает редко, и это два индексных чтения.
