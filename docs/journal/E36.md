# E36 — Бот падал от нехватки памяти, ответы терялись с 502

## Спека

Разбор открытых багов из `/bug` (ноябрь 2026) начался с жалобы Николая (#23): «карточки вообще не
засчитываются». Цифры в жалобе сошлись с журналом — 96 верных ответов по 3 HP и 82 забытых по 1.5 HP
за 20 ноября, то есть правило затухания «Забыл» (E2) работало как задумано. Но в той же переписке
был второй баг (#24): «писалось, что карточка не засчиталась, дальше показывало ошибку 502».

Приёмка:

1. Обе модели Kokoro делят один набор весов; память процесса не выше 1.4 ГБ; оба акцента озвучиваются.
2. Приложение повторяет безопасный запрос один раз, если сервер ответил 502, и показывает ошибку
   только после второго отказа.
3. Повтор не засчитывает ответ дважды — защита на сервере (`reps`, `requestId`).
4. После деплоя память бота ниже 2 ГБ, `/status` и озвучка работают.

## Что было не так

Диагноз по проду:

```
OOM-убийства eng-bot.service:  9 раз с 8 ноября (последнее 21.11)
память сервиса:                2.49 ГБ из 3.9 ГБ, своп 0 байт
из них kokoro_server.py:       1.85 ГБ
```

20 ноября в 11:30:08 systemd пишет `A process of this unit has been killed by the OOM killer`, а в
`/var/log/nginx/access.log` в ту же секунду три `POST /api/answer` отвечают **502**. Ответы,
которые люди отправили в этот момент, потерялись: карточка осталась неоценённой, приложение
показало «Ответ не сохранён».

Причина памяти — `tools/tts/kokoro_server.py` создавал `KPipeline` на каждый акцент:

```python
pipelines = {accent: KPipeline(lang_code=lang, repo_id=...) for accent, (lang, _) in VOICES.items()}
```

Каждый `KPipeline` с `model=True` (по умолчанию) загружает свою копию весов.

## Замеры

Пробы на VPS (`/opt/eng-bot-git`, python из `tools/tts/.venv`):

| Вариант | Память (ru_maxrss) | Итог |
| --- | --- | --- |
| два `KPipeline` (как было) | **1714 МБ** | **убит OOM, exit 137** |
| `KModel` + два `KPipeline(model=…)` | **1299 МБ** | работает, оба акцента |
| один `KPipeline` (для сравнения) | 1232 МБ | — |

Загрузка одной модели — 11.9 с, синтез фразы — 1.2–2.3 с. Загрузка общей модели и двух обвязок —
3.0 с (обвязка на язык стоит 0.6–1.0 с), то есть правка ещё и ускорила старт.

## Что сделано

- **`tools/tts/kokoro_server.py`**: модель грузится один раз (`KModel`), `KPipeline` получает её
  параметром `model=`. Обвязка на акцент осталась своя — у неё свой фонемайзер языка, и это
  единственное, что действительно должно различаться.
- **`app/src/retry.ts`** (новый): `retryServerDown` — одна повторная попытка на 502/503/504 с паузой
  700 мс. Список кодов и пауза — экспортированные константы, `sleep` подменяется в тестах.
- **`app/src/api.ts`**: добавлен `postRetry`, на него переведены шесть запросов, которые сервер сам
  защищает от двойного срабатывания: `/api/answer`, `/api/undo`, `/api/check`, `/api/grammar/answer`,
  `/api/boss/combat`, `/api/boss/upgrade`.
- **Тесты**: `tests/retry-server-down.test.ts` (7) и `tests/kokoro-single-model.test.ts` (3).

## Решения и причины

- **Общая модель, а не ленивая загрузка по акценту.** Ленивая тоже экономила бы память, но ценой
  задержки: первая же фраза другого акцента ждала бы 12 секунд. Общая модель даёт обе сразу за 3 с
  и не тратит память дважды — это лучше по обоим параметрам, а не компромисс.
- **Повтор ровно один.** Сервис поднимается за секунды; если не поднялся — честнее показать ошибку,
  чем крутить запросы. Две попытки покрывают окно перезапуска, три уже маскируют настоящую поломку.
- **Повторяются не все POST.** Черновики и квоты (`/api/words/prepare`, `/api/words/:id/mnemonic`,
  генерация) не повторяются: повтор потратил бы лимит дважды. «Сохранить ошибки» (`/api/mistakes`)
  не повторяется: сервер забирает черновик из памяти при первом вызове, и повтор дописал бы ошибки
  ещё раз. Список безопасных запросов — в комментарии к `postRetry`.
- **Сеть без кода не повторяется.** `TypeError: Failed to fetch` — это не «сервер не ответил»,
  а оборванная связь на телефоне; повтор там не помогает и только добавляет задержку.
- **Тест Kokoro читает скрипт, а не запускает модель.** Запуск — 1.2 ГБ и 12 с, а веса есть не в
  каждом окружении. Проверяется то, что ломает память: `KPipeline` не должен создавать модель сам.
  Настоящий прогон с обоими акцентами делался на проде вручную — числа выше.

npm run typecheck                            → чисто
cd app && npm run build                      → tsc чисто, vite собрал (490 кБ js)

старый retry.ts  → 4 из 7 тестов падают (повтора нет вовсе)

```

Прогон нового сервера на VPS (копия в `/tmp`, python из `tools/tts/.venv`):

```
printf '{"id":1,...,"accent":"us"} {"id":2,...,"accent":"uk"}' | python /tmp/kokoro_server.py
→ {"ready": true} {"id": 1, "ok": true} {"id": 2, "ok": true}

Проба «два `KPipeline`» на VPS дала `EXIT=137` и запись OOM-killer'а в `dmesg` — то есть старая
версия действительно не влезает в память, и это не догадка, а воспроизведение.

## Известные ограничения

- **Свопа на VPS по-прежнему нет.** Правка убирает 415 МБ и главную причину, но запас остаётся
  небольшим: 4 ГБ на бота, TTS, Docker-контейнер и системные службы. Своп 2 ГБ был бы страховкой;
  в задачу не вошёл — это настройка сервера, а не кода, и её стоит делать отдельно.
- **Повтор не спасает, если запрос потерялся ПОСЛЕ обработки, но ДО ответа.** Тогда повтор увидит
  `reps` уже сдвинутым и вернёт `stale` — двойного зачёта не будет, но человек увидит «Ответ уже
  учтён». Это лучше потери, и других последствий нет.
- **У грамматики повтор может дописать ошибку в работу над ошибками дважды.** Проверил все шесть:
  `/api/answer`, `/api/check`, `/api/undo` защищены сверкой `reps`, `/api/boss/combat` — `requestId`,
  `/api/boss/upgrade` — условным обновлением по текущему уровню и балансу (второй вызов получает
  «бедно», а не списывает ещё раз). У `/api/grammar/answer` урон боссу идемпотентен (`requestId`
  `grammar:<user>:<exercise>`), `done` второй раз не двигается (позиция уже сдвинута), но `streak`
  вырастет на единицу, а неверный ответ ещё раз попадёт в `mistakes`. Цена — дубль в списке ошибок,
  и только если сервер упал ровно между обработкой и ответом; альтернатива (не повторять грамматику)
  означала бы терять ответы людей. Оставил повтор и записал это здесь.
- **Другие 502 на проде не проверялись.** В логах их 544 за всё время, но почти все — сканеры,
  стучавшиеся в чужие пути (`/api/v1/config`, `/.env`). К нашим эндпоинтам относятся единицы.
- **Замер памяти после деплоя — разовый.** Постоянного наблюдения за `MemoryCurrent` нет; если
  утечка есть, её снова увидят только по OOM-записям в журнале.
