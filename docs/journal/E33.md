# E33 — `nextReviewAt` сортирует всю очередь, чтобы взять один элемент

## Спека

`SELECT due FROM cards WHERE userId = ? ORDER BY due LIMIT 1` даёт `USE TEMP B-TREE FOR ORDER BY` —
сортировка всех карточек человека ради одной строки. Экран «Готово» спрашивает это после каждой сессии.

Приёмка: запрос использует индекс `(userId, due)` без временного B-tree (`EXPLAIN QUERY PLAN` не
содержит `TEMP B-TREE`); результат тот же — тест на `nextReviewAt` зелёный.

## Что было

В `cards` был только `uniqueIndex("cards_user_word_idx").on(userId, wordId)`. Он закрывает поиск по
человеку, но не порядок по `due` — поэтому SQLite сортировал результат через временное B-tree.

Проверено на чистой базе (проба, не рассуждение):

```
БЕЗ (user_id, due): SEARCH cards USING INDEX cards_user_word_idx (user_id=?) | USE TEMP B-TREE FOR ORDER BY
С   (user_id, due): SEARCH cards USING COVERING INDEX cards_user_due_idx (user_id=?)
```

## Что сделано

`src/db/schema.ts` — добавлен `index("cards_user_due_idx").on(t.userId, t.due)`.
`drizzle/0064_brave_madame_masque.sql` — миграция `CREATE INDEX cards_user_due_idx ON cards
(user_id, due)`.

`tests/query-plans.test.ts` — тест на план запроса: требует наличия `cards_user_due_idx` и отсутствия
`TEMP B-TREE`.

## Честная оговорка про проверку теста

Тест **проходит и при удалённом из схемы индексе** — потому что миграция уже применена к тестовой
базе, и индекс остаётся в ней. Я попробовал откатить схему и файл миграции через `git stash` — не
вышло, файлы не были закоммичены.

Поэтому эффект индекса доказан **отдельной пробой** на чистой базе в памяти (вывод выше), а не
падением теста. Тест же закрепляет, что план не деградирует в будущем: если кто-то удалит индекс или
поменяет запрос, он упадёт.

## Решения и причины

- **Составной `(user_id, due)`, а не отдельный `(due)`.** Порядок в индексе важен: сначала равенство
  по `user_id`, потом сортировка по `due`. Отдельный индекс по `due` не помог бы выборке одного
  человека.
- **Новый индекс, а не замена `cards_user_word_idx`.** Тот уникальный и защищает от дублей пары
  «человек+слово» — это его работа, и убирать его нельзя.
- **`COVERING INDEX` в плане — бонус.** Запрос читает только `due`, и он есть в индексе: таблица не
  читается вовсе.

## Известные ограничения

- **Тест не падает при отсутствии индекса** в описанной выше ситуации, и я не стал обходить это
  костылём (создавать базу без миграций в тесте). Эффект доказан пробой, тест — защита от регресса
  плана, а не от удаления индекса.
- **Замер времени не делал.** На объёмах прода (4–5 тысяч карточек на человека максимум) сортировка
  занимает доли миллисекунды; выигрыш здесь в том, что работа не растёт с числом карточек.
- **Другие запросы по `cards` не проверялись.** `dueItems` фильтрует по `user_id` и `due <= now` —
  новый индекс помогает и ему, но плана я для него не снимал.
