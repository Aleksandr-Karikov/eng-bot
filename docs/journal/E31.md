# E31 — `settingsText` содержит HTML-теги, но отправляется без `parse_mode`

## Спека

`/settings` отвечает `ctx.reply(settingsText(ctx.user), { reply_markup })` без `{ ...HTML }`, хотя
строка собирает `<b>Озвучка карточек в приложении.</b>` и `<b>${voiceLabel(user)}</b>`. Telegram
показывает теги буквально — человек читает «<b>Озвучка…</b>». То же в двух ветках `editMessageText`.

Приёмка: `/settings` и все его экраны показывают жирный текст, теги не видны; тест проверяет
`parse_mode` в вызове.

## Что было

Пять мест отправляли `settingsText` без разметки:

```
src/bot/handlers/stats.ts:126  /settings, главный экран
src/bot/handlers/stats.ts:181  экран «Напоминание»
src/bot/handlers/stats.ts:190  экран «Озвучка»
src/bot/handlers/stats.ts:208  переход между экранами
src/bot/handlers/stats.ts:201  экран «Новые слова» — здесь `...HTML` БЫЛ, остальные четыре без
```

То есть один экран из пяти вёл себя правильно, и это делало дефект незаметным при беглом взгляде.

## Что сделано

`src/bot/handlers/stats.ts` — `{ ...HTML, reply_markup: … }` во всех пяти местах.

`tests/settings-html.test.ts` — два теста: главный экран и экран «Озвучка» (через нажатие кнопки, то
есть тем путём, которым идёт человек). Проверяется `parse_mode` в реальном вызове Telegram, а не
строка текста.

## Решения и причины

- **Проверка через бот-харнесс, а не на строке.** Дефект был не в тексте (там теги правильные), а в
  том, как его отправляют. Тест на `settingsText` прошёл бы и до правки.
- **Правка во всех пяти местах сразу.** Четыре из них были одинаково неправы; чинить только `/settings`
  значило бы оставить человека читать теги при заходе в «Озвучку».

## Проверки

```
npx vitest run tests/settings-html.test.ts  → 2 tests passed
npx tsc --noEmit                            → чисто
```

Тесты проверены на старом коде (`git stash push src/bot/handlers/stats.ts`):

```
× главный экран /settings идёт с parse_mode HTML
  → expected undefined to be 'HTML'
× экраны «Озвучка» и «Напоминание» тоже с разметкой
  → expected undefined to be 'HTML'
```

## Известные ограничения

- **Экраны `modes`, `card`, `new`, `show` тестом не покрыты.** Для них проверка та же по смыслу
  (общий `settingsText`), но отдельного теста на каждый нет: они идут через тот же путь 208, который
  теперь покрыт косвенно.
- **Визуально в Telegram не проверял.** Тест подтверждает, что `parse_mode` передан; как это выглядит
  на экране — свойство клиента Telegram, а не кода.
