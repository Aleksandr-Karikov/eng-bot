# План проекта

Добавляй задачу, когда появится требование к проекту. Открытая строка содержит спеку, приёмку и
текущее состояние; после завершения подробности переносятся в `journal/E<номер>.md`. Номер не
переиспользуется. Создавай следующий свободный `E<номер>`.

Формат открытой задачи:

```md
- [ ] **E1** — Название. **Спека:** цель, сценарий, состояния, данные и права (если применимо). **Приёмка:** наблюдаемый результат и необходимые проверки. ➡️ **Сейчас:** что известно, что мешает, следующий шаг.
```

Правила ведения — в [CONTRIBUTING.md](CONTRIBUTING.md). Индекс [INDEX.md](INDEX.md) генерируется
командой `npm run docs:index`; руками его не правь.

## Задачи

Первый блок — расхождения между задуманным и работающим, найденные разбором босса недели
([boss-next-plan.md](boss-next-plan.md) — источник разбора, история и гипотезы, а не список задач).
Каждый пункт сверен с кодом; ссылки на числа стенда и живого прогона остаются в исходном документе.

- [ ] **E1** — Кнопка «Ударить босса» не работает при настройке по умолчанию. **Спека:** запас урона `bankDamage` по умолчанию выключен, поэтому `damageBalanceDeci` считает баланс только по `review_logs.banked = true` и возвращает 0. `reserveHit` получает `available = 0`, `hit.spend = 0`, кнопка ручного удара отрисовывается `disabled` и без подсказки, почему. Человек видит главное действие боя мёртвым и не понимает, что для него нужно включить «Копить урон». **Приёмка:** при выключенном «Копить урон» кнопка либо работает на небанковских ответах, либо явно объясняет и ведёт к нужной настройке; тест `tests/combat*.test.ts` фиксирует выбранное поведение, экран босса проверен в Mini App. ➡️ **Сейчас:** поведение подтверждено по коду (`src/services/combat.ts`, `src/services/combat-ledger.ts`, `app/src/Boss.tsx`). **Решено:** экономику не трогать — кнопка остаётся `disabled`, но рядом появляется объяснение и кнопка «Включить копить урон», которая ведёт к настройке. Проверка: `tests/boss.test.ts` на выключенный `bankDamage`.
- [ ] **E2** — «Забыл» возвращает карточку через минуту и бесконечно кормит босса уроном. **Спека:** FSRS отдаёт `again` через 1 минуту, а `answerWeight("again")` равен 1, поэтому одна карточка даёт HP без предела. Награждаются нажатия, а не память, и цель следующей недели при этом растёт. **Приёмка:** повторные «Забыл» по одной карточке не дают неограниченный урон; ограничение названо в задаче и покрыто тестом, который падает при возврате старого поведения. **Решено:** затухание по числу повторов подряд — урон за «Забыл» падает 1 → 0.5 → 0.25, после третьего подряд даёт 0. Учит честно и не требует новых таблиц: число повторов подряд выводится из `review_logs`. ➡️ **Сейчас:** интервал измерен прогоном на `src/srs/srs.ts` (again → 1 мин, hard → 6, good → 10, easy → 11520). Масштаб проблемы по копии прод-базы: до 15 «Забыл» на одну карточку, всего `again` — 2634 из 6635 ответов. Затухание считается в `answerWeight` (`src/services/goals.ts`), туда надо передать число провалов подряд; `roomReviews` его уже читает из логов.
- [ ] **E3** — Цель недели сжимается от усилений, и глубина не копится. **Спека:** цель недели считается как `autoGoal(raw)` × `BASE_WEIGHT`, где `raw` — число ответов прошлой недели. Усиление поднимает урон за ответ, поэтому для той же цели нужно меньше ответов, `raw` падает, и следующая цель становится **меньше** — человек не «доходит дальше», а откатывается. При этом ладдер боссов (`tierHp`, 8 ступеней × рост 1.3, круги) уже устроен как рогалик: его база фиксирована (`LADDER_BASE_HP`), и глубина растёт от прокачки — это работает правильно (`src/services/boss.ts:213-214`). **Приёмка:** цель недели не зависит от усиления — либо фиксируется по рекорду комнаты, либо считается от нанесённого урона, а не от числа ответов; глубина ладдера зависит от личного рекорда и растёт при росте уровня. Тест: две одинаковые недели с разным уровнем усиления дают одинаковую цель и разную глубину. **Решено:** разорвать связь — цель фиксированная, глубина от рекорда. ➡️ **Сейчас:** связь подтверждена замером: `answers=50 → target=120 HP`, `answers=200 → target=440 HP`, а уровень 10 (+100% урона) вдвое уменьшает нужное число ответов, то есть роняет цель следующей недели. Меняет исторические числа в `/goal` — нужен сброс или явная пометка периода. Связано с E4 (обе правят одну формулу) — разумно делать одним блоком.
- [ ] **E4** — Честность наказывается: «Забыл» повышает цель следующей недели. **Спека:** `raw` в `roomReviews` считает все ответы подряд, включая `again`. Ошибки раздувают цель следующей недели, поэтому врать «Помню» выгоднее, чем признаться. **Приёмка:** цель растёт только от ответов, отражающих прогресс, либо правило названо явно; тест покрывает неделю с преобладанием `again`. ➡️ **Сейчас:** подтверждено по `src/services/goals.ts`. Связана с E3: обе правят одну формулу, их разумно свести в один блок. **Решено:** вместе с E3 цель перестаёт считаться от числа ответов, поэтому `raw` больше не участвует — правку делать в той же ветке.
- [ ] **E5** — «Уже знаю» даёт максимальный базовый урон без проверки. **Спека:** `markKnown` отправляет `easy` для карточки в состоянии `New` с `reps = 0`, то есть 3 HP за нажатие — максимум базовой таблицы без усилия. Ограничение новыми словами не даёт эксплойта, но перекашивает вклад между участниками. **Приёмка:** решение либо оставляет поведение и объясняет его в интерфейсе, либо требует проверки; тест фиксирует выбранное правило. ➡️ **Сейчас:** подтверждено по `src/services/review.ts` и `src/services/goals.ts`. **Решено:** урон в общую цель не давать — свайп «уже знаю» это знакомство, а не работа. `markKnown` продолжает закрывать карточку, но `answerWeight` для стадии `know` возвращает 0. Проверка: тест, что «уже знаю» не двигает `/goal`, а карточка уходит из очереди.
- [ ] **E6** — Неделя считается по одному поясу, напоминание приходит по другому. **Спека:** `rooms.timezone` заполняется поясом автора при создании и по умолчанию `Asia/Novosibirsk`, а у пользователя пояс по умолчанию `Europe/Moscow` и напоминание в 20:00 считается по поясу пользователя. В комнате с НСК-поясом напоминание «последний шанс» приходит после фактического сброса недели. Трофеи «ночной» и «ранняя птица» тоже считают часы по поясу комнаты для всех участников. **Приёмка:** правило пояса описано одним местом и совпадает для недели, напоминания и трофеев; тест покрывает участника в одном поясе и комнату в другом. ➡️ **Сейчас:** подтверждено по `src/services/digest.ts`, `src/services/trophies.ts`, `drizzle/0055_cool_speed_demon.sql`, `src/db/schema.ts`. **Решено:** напоминание — по личному поясу (человеку удобно его время), граница недели, трофеи и «последний шанс» — по поясу комнаты. Правило зафиксировать одним местом и назвать в `docs/architecture.md`.
- [ ] **E7** — Выключение `BOSS_ENABLED=0` меняет числа, вопреки обещанию ранбука. **Спека:** `reviewDamage` считает урон с усилением независимо от `active`, а `banked` сбрасывается в `false`. `roomReviews` кладёт в прогресс только записи с `banked = false`, поэтому при выключении режима банковские ответы попадают в `/goal`, а при включении — нет. Комментарий в `src/services/boss.ts` и `docs/server-runbook.md` обещают «те же числа». **Приёмка:** выключение режима не меняет прогресс `/goal`, либо обещание в коде и ранбуке исправлено; тест про две одинаковые недели с разным флагом. ➡️ **Сейчас:** подтверждено по `src/services/review.ts`, `src/services/goals.ts`, `src/services/boss.ts`. Правка ранбука входит в ту же задачу, отдельной не заводить.
- [ ] **E8** — Владелец личного словаря получает «Герой недели» сам о себе. **Спека:** `weeklyReportText` берёт первую строку таблицы как героя недели; в личной комнате первая строка — её единственный участник, и поздравление с победой над собой приходит ему же в личку. **Приёмка:** при одном участнике строка героя не выводится; тест на дайджест личной комнаты. ➡️ **Сейчас:** подтверждено по `src/bot/texts.ts` и `src/services/digest.ts`. Комнат с одним участником много, это больше, чем косметика.
- [ ] **E9** — Mini App при выключенном режиме показывает неверный экран. **Спека:** сервер отдаёт `enabled`, но клиент его не читает: при `enabled: false` и отсутствии `boss` показывается «Боссу нужна комната» с советом `/room` вместо честного «режим выключен». **Приёмка:** выключенный режим и отсутствие комнаты различаются на экране, каждый ведёт к правильному действию; тест на `app/src` и проверка экрана. ➡️ **Сейчас:** подтверждено по `src/app/api.ts` и `app/src/Boss.tsx`: `data.enabled` объявлен в типах, но не используется.
- [ ] **E10** — Контент экрана босса уезжает под системную панель. **Спека:** у `.screen` нижний отступ 96 px и `env(safe-area-inset-bottom)` у панели, а `.boss-screen` перебивает отступ на 24 px при той же специфичности и `safe-area` не содержит. **Приёмка:** на устройстве с home indicator контент не перекрывается; проверено на узкой ширине, правка отражена в `app/src/styles.css`. **Решено:** править `padding-bottom` у `.boss-screen` с учётом `safe-area`, как у панели; проверка на устройстве остаётся желательной, но правило проверяемо и по коду: `.boss-screen` объявлен позже `.screen` (строка 377 против 74) и с той же специфичностью, поэтому перебивает `padding-bottom: 96px` на 24px. ➡️ **Сейчас:** подтверждено по `app/src/styles.css`.
- [ ] **E11** — Недельная работа трофеев выполняется каждую минуту. **Спека:** `sendTrophies` вызывается в тике напоминаний с интервалом по умолчанию 60 секунд, а `collectTrophies` на каждом вызове читает всю таблицу `trophies`, все комнаты и считает `weekFacts` по каждой. Это примерно 10 080 прогонов в неделю вместо одного. **Приёмка:** недельный расчёт выполняется по признаку закрытой недели, а не по тику; тест проверяет, что повторные тики в одну неделю не пересчитывают; идемпотентность выдачи трофеев сохраняется. ➡️ **Сейчас:** подтверждено по `src/reminder-loop.ts` и `src/services/trophies.ts`. Похоже на `rooms.goalReachedWeek` — тот же приём стоит применить.
- [ ] **E12** — Победа в чате звучит как отчёт по цели, добивающий удар не называется. **Спека:** `finalBlow` считается в `src/services/boss.ts` и уходит в Mini App, но в чат не попадает: `goalReachedText` перечисляет только счёт и лидера. Комнату никто не поздравляет с добиванием, а сообщение уходит всем участникам, включая тех, кто режим выключил. **Приёмка:** в чат приходит текст с добивающим ударом и фазой; выключившим режим сообщение не уходит; тест на текст и на фильтр получателей. ➡️ **Сейчас:** подтверждено по `src/services/boss.ts`, `src/bot/texts.ts`, `src/reminder-loop.ts`.
- [ ] **E13** — Измерить эффект режима босса. **Спека:** `grep boss` по аналитике не даёт совпадений, поэтому эффект режима неизвестен и любая новая механика — предположение. Нужен минимум: таблица `boss_events(user_id, room_id, kind, week, dedupe, at)` с `kind` из `seen|open|hit|buy|win`, уникальный индекс `(user_id, kind, dedupe)`, запись только `onConflictDoNothing`; пять чисел в `/status` — экспозиция, открытия, ударившие, купившие, вернувшиеся; дата переключения `users.mode_boss` для сравнения окнами по 14 дней. Попутно убрать чтения без `where` в `trainerReport` и `sourceSummary` и сузить `withCombatLock` до денежных операций: сейчас он сериализует все ответы всех людей в одном процессе. **Приёмка:** `/status` показывает пять чисел, события не дублируются при повторной записи, схема и миграция сгенерированы (`npm run db:generate`) и закоммичены. **Решено:** делать событийную аналитику. ➡️ **Сейчас:** подтверждено по `src/reminder-loop.ts`, `src/services/combat-ledger.ts`, `src/bot/handlers/status.ts`. A/B-платформы нет: сравнение по переключениям `users.mode_boss` окнами по 14 дней на тех же людях.

- [ ] **E24** — Два счётчика слов пишутся раздельно, и на границе лимит обходится. **Спека:** `checkAndCountWord` читает дневной и недельный счётчики, потом пишет оба через `Promise.all`. Порознь это правильно (отказ по недельному не съедает дневной), но между чтением и записью остаётся `await`, поэтому два параллельных добавления при остатке 1 могут оба пройти. Ограничение записано в журнале E15 как «требует атомарности по двум строкам». **Проверено, что это решаемо без `db.transaction`:** одна инструкция `INSERT … VALUES (две строки) ON CONFLICT … DO UPDATE SET count = count + 1 WHERE (kind = 'add_word' AND count < 50) OR (kind = 'add_word_week' AND count < 200) RETURNING kind, count` — `WHERE` видит существующую строку, поэтому условие можно задать по каждой строке отдельно. Проба: при дневном на пределе и недельном с запасом инструкция вернула только недельную строку и не тронула дневную. **Приёмка:** `checkAndCountWord` — одна инструкция с по-строчными условиями; при исчерпанном недельном дневной не растёт (проверяется `returning`: вернулись либо обе строки, либо ни одной); тест `Promise.all` на 3× лимит при остатке 1 утверждает, что прошло ровно 1; инварианты целы — `db.transaction` не появился, sqlite-специфичных методов нет, `ON CONFLICT … DO UPDATE … WHERE … RETURNING` есть и в Postgres. ➡️ **Сейчас:** подход проверен пробой на `usageCounters` (см. выше). Ограничение: при отказе нужно понять, какой именно счётчик упёрся, чтобы показать правильный текст отказа — из `returning` видно, какие строки прошли, но не видно, какой был предел; значит лимиты надо передавать в SQL и разбирать результат. Слои — только `src/services/limits.ts`.

- [ ] **E25** — Лимит на слова держится тремя разными способами и в трёх местах. **Спека:** после E14–E16 и E24 останется три представления одного правила: `wordsLeft` (читает два счётчика), `checkAndCountWord` (пишет два), и снимок `batch.left` в пачке `/text`, который живёт с момента показа списка до нажатия «✅ Добавить».
