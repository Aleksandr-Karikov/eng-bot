---
name: repo-close
description: Закрыть продуктовую задачу с честной сверкой приёмки, проверками, журналом и обновлением индекса. Используй после завершения реализации, когда задача была заведена в плане.
---

1. Проверь `git status`, дифф, строку задачи и поздние решения владельца. Если часть приёмки не сделана, задачу оставь открытой и запиши остаток в `➡️ **Сейчас:**`; статус «готово» не подменяет факты.
2. Запусти гейт и дополнительные проверки по затронутым путям: `npm test && npm run typecheck`, при правке Mini App — `cd app && npm run build`. Для экрана или текста в чате проверь пользовательский сценарий по `repo-screen`. Миграции БД: `npm run db:generate` и файл в `drizzle/` закоммичен. Красный результат окружения (занятый порт, второй `npm test`, недоступный внешний API) назови отдельно. Не записывай тест, который не выполнялся.
3. В журнале `docs/journal/E<номер>.md` сохрани первоначальную спеку, что сделано, решения и их причины, сознательно отложенное, фактические команды и результаты, известные ограничения. Для заметного изменения интерфейса назови экран, размеры, темы и результат проверки.
4. Отметь задачу закрытой только после журнала: `- [x] **E<номер>** — Название. [журнал](journal/E<номер>.md).` Затем `npm run docs:index && npm run docs:check`. Правь соседние документы только там, где они разошлись с реальностью. В документах не пиши числа, которые меняются с каждым коммитом (тестов, таблиц, пользователей) — их показывают `npm test` и `/status`.
5. Перед коммитом пройди `repo-review`. Проверь staged-файлы на секреты и случайные артефакты: `.env`, `data/`, собранный `app/dist/`. Починив баг из `/bug`, упомяни его номер в сообщении коммита. Сообщение коммита описывает результат и проверки, а не список изменённых файлов.
